# DompetKu v2 · S13 (Tujuan tabungan, 1 dompet = 1 tujuan aktif) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: superpowers:subagent-driven-development (implementer per task, task review, fix loop, review akhir). Model: DB/uang/server = terkuat (opus); UI = sonnet dengan lensa desain (design reviewer di tiap task UI).

**Goal:** Membuka M4 (IPD §6 S13, gerbang "bagian T11"): pengguna membuat **tujuan tabungan** (nama, target, tanggal target opsional) yang menempel pada **satu dompet tabungan**; progres dihitung SQL dari saldo dompet itu terhadap target, tanpa kolom progres tersimpan; dompet yang sama tidak bisa punya dua tujuan aktif (constraint DB, PRD:111). Tujuan bisa diubah, diselesaikan, diarsipkan, dan dipulihkan. Tersedia di Pribadi dan Bersama. Bagian aset/saham dari T11 (repro S5: edit setoran ke aset) dan gerbang M4 penuh = S14.

**Definisi "bagian T11" (inferensi, butuh persetujuan pemilik):** isi T11 asli (INT §4 repo v1) tidak ada di repo (`REGISTRY.md` baris T11: "skenario goal/aset INT §4"). Sumber yang ada: PRD:111 dan :158, qa.md Lampiran A baris M4 ("1 dompet = 1 goal aktif", "proyeksi goal", "setor ke goal"), S-43 (`docs/team/round1/product-owner.md:225`: "satu rumus di DB dipakai semua layar", "Perlu Rp X/bulan benar", "tersedia di Bersama"). Definisi kerja S13 ada di K9.

**Status spesifikasi:** yang ditetapkan: 1 dompet = 1 tujuan (spec induk §7, keputusan pemilik 2026-10-29), tujuan per ruang (spec §5.4), tujuan kedua pada dompet sama ditolak constraint (PRD:111, IPD S13 risiko), satu rumus progres di DB, "Perlu Rp X/bulan", tersedia di Bersama (S-43), emoji hanya bila pengguna memilihnya (ui-ux:270). Yang **tidak** ditetapkan: skema (BSD:2714 hanya "polanya sama"), pocket mana yang boleh punya tujuan, dasar progres (saldo dompet atau setoran sejak tujuan dibuat), arti "bulan" untuk laju tabung, apa yang terjadi saat tujuan tercapai, arsip dompet bertujuan, letak UI. S-43 menyebut "setor/cairkan = transfer bertanda goal": plan ini **tidak** memakai penanda (K2) karena 1 dompet = 1 tujuan membuat setiap gerak dompet itu sudah gerak tujuan.

**Arsitektur:** Pola S11 (tabel + API terpisah) dan S12 (angka dari view, tanpa kolom tersimpan). Tabel baru `app.goals` (ruang Pribadi atau Bersama, FK komposit `(space_id, account_id)` ke `app.accounts`, `status` `active`/`completed`/`archived`), **indeks unik parsial `goals_one_active_per_account on app.goals (account_id) where status = 'active'`** sebagai constraint "1 dompet = 1 tujuan aktif" (dua `create_goal` paralel: yang kedua `23505` dipetakan ke `DK409 goal_exists`). Trigger penjaga: dompet harus `pocket = 'tabungan'` (K3), satu ruang, belum diarsip saat tujuan dibuat/diaktifkan. Progres = view `app.goal_progress` (`security_invoker`) dari `app.account_balances`: `saved = max(0, saldo)`, `remaining = max(0, target − saldo)`, `pct = least(100, floor(saved·100/target))`, `reached = saldo ≥ target`, `per_period` = laju tabung (K5); entri tidak berubah (tanpa `entry_kind`, tanpa `goal_id` di `entries`, tanpa kelas laporan baru). Akibatnya: **"aman dipakai"** tidak berubah (hanya operasional, `0120:49`); **kekayaan bersih** tidak berubah (tabungan sudah dihitung, `0134:183`, `account-list-view.tsx:106`); **Laporan/Ekspor/Transaksi** tidak berubah (setor ke dompet tabungan = transfer `x_transfer` atau `space_transfer` yang sudah ada; pengeluaran dari dompet tabungan tetap pengeluaran). Tulis lewat `api.*` DEFINER (`app.assert_member` lebih dulu, idempoten `client_id` untuk `create_goal`), baca INVOKER STABLE. RLS ENABLE + FORCE, tulis hanya `dompetku_api`; tujuan Pribadi pasangan tidak terbaca (B-tes dua user). Aritmetika di SQL; UI tidak menjumlah atau menghitung persen.

**Cabang:** `ccr-6b15bf5f-1cnpb6` (di-reset ke `main` `c1e7ea8`, S12 sudah merge; sesi cloud hanya boleh push ke cabang ini, bukan `claude/s13-<topik>` seperti CLAUDE.md). Tanpa PR sampai CI/review siap; **merge = deploy + migrasi `0137`–`0138` di produksi** (maju-saja, tanpa langkah VM baru).
